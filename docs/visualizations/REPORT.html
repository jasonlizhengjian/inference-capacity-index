STEP 1 · DEFINE THE COMPARISON

Choose a workload and an architecture basket

1 · Why 256Ki context?

Trace-informed study choice

Jason’s earlier workload-distribution analysis motivated roughly 256K as a representative long-context agent workload, conditional on the harness and compaction policy. It is not a midpoint between product context limits. We fix 262,144 tokens to keep the comparison controlled; performance at this context need not equal average performance over a distribution.

Background: Epoch AI agent-capacity research and its associated code and data. The exact 256Ki choice is the author’s modeling judgment informed by that work, not a pooled mean recomputed here. The later warm-cache cohort is selected around this context; it does not independently prove the choice.

We study long-context, warm-cache inference: each request has an existing 262,144-token context (256Ki tokens), with the cache required by its architecture already resident. Sliding-window layers retain only their window, while other layers follow their own cache rules. Decode generates output from this state; prefill processes new input using the existing prefix. Keeping this workload fixed lets us compare hardware under the same conditions.[1]

One active workload

At each target output speed, count concurrent decoding requests per total serving chip. The denominator will include the prefill chips needed to supply those requests’ input—not just the chips executing decode.

Four equally weighted architectures

2 · Model selection and MAI-2 assumptions

Architecture coverage; disclosed and assumed dimensions

GLM supplies sparse attention; Kimi supplies a large MLA-based model; Qwen supplies full GQA; MAI-2 2.8T supplies sliding-window/global attention and latent MoE. Equal weights broaden architectural coverage; they do not imply known traffic shares, equal quality or complete frontier coverage.

The MAI-2 reconstruction follows Microsoft’s disclosed 102 layers, hidden width 8,704, 85 local and 17 global attention layers, 16 local and 2 global KV heads, 96 query heads, top-7 of 512 routed experts plus one shared expert, routed latent dimension 4,096 and expert intermediate width 4,352.

It is an informed proxy, not an exact production implementation. Head size 128, window 512 and vocabulary 200,019 are inherited from the predecessor; shared intermediate width 4,352 is assumed. Latent projections are conservatively replicated under TP.

Sources: MAI-Base-2 disclosure and MAI-Base-1 report.

What is counted as an active agent

The numerator is concurrent decoding requests. The denominator includes both the decode chips and the prefill chips needed to supply their new input. The plotted label is therefore “decode concurrency per total serving chip.” It does not count extra agents currently prefilling, waiting or using tools. The worked example in step 5 shows how to count both pools.

STEP 2 · ESTIMATE A FORWARD PASS

Use AISim to translate the workload into execution time

3 · Why analytical SOL?

Comparison framework

Hardware-specification-based operation costs let us compare platforms without requiring equally optimized serving code on every device. This is more structured than a single aggregate FLOP or bandwidth ratio, but not a cycle-accurate chip simulator. An omitted optimization or incorrect traffic assumption can change the modeled ceiling.

We apply no achieved-performance multiplier. Earlier benchmark grounding motivates efficiency scenarios, not a universal guarantee that every chip achieves at least 50% of SOL.

NVIDIA AISimulate is an analytical inference-performance model. We give it the architecture, hardware specifications, batch and parallelism. It estimates operation-level compute, memory movement and communication costs without running the model on the target accelerator.[3]

What does “speed of light” (SOL) mean here?

It is a hardware-specification-based estimate of how fast the modeled work could run using peak compute and data-transfer rates. For a roofline-modeled operation, we calculate both the time needed to do the arithmetic and the time needed to move its data; the larger time sets its limit. We then account for required communication and the sequence of operations.

100% of modeled SOL means matching that predicted speed—not keeping every resource at 100% utilization. An operation can use all its memory bandwidth while leaving much of its compute idle. The index reports this idealized performance, not measured production speed, and applies no blanket efficiency discount.

Model + hardware + configuration → operation timings → full iteration time
TPS/user = accepted output tokens per iteration ÷ iteration time

4 · Why AL3 with nextn3?

Measured origin; shared assumption

InferenceX’s Kimi-K3 SPEED-Bench coding reference reports AL = 3.00 for three speculative tokens, measured with vLLM DSpark. That motivates this operating point. Applying the same accepted length to GLM, Qwen and MAI-2 is a controlled assumption, not a measurement of those models or every workload.

Acceptance reference. Four target verification positions do not imply a 75% independent acceptance probability per drafted token. Draft cost still follows each native AISim graph, not one shared measured DSpark implementation.

The decode study uses nextn3 / AL3: four target verification positions and an assumed average of three accepted output tokens per iteration. Native verification and draft work are included.[4]

TPS/user is average output tokens per second for one decoding request. TPOT is its reciprocal, in seconds per output token. With speculative decoding these are averages: tokens can arrive in bursts, not at evenly spaced intervals.

Inside AISim: a layer diagram, roofline equations and implementation details

What is AISim? AISimulate (AISim) is NVIDIA’s open-source performance-modeling toolkit for LLM inference, and the successor to AIConfigurator. It predicts execution time from a model’s architecture, its deployment configuration and the hardware’s resources. We use its operation-level speed-of-light (SOL) mode: an analytical calculation that runs on a CPU, without needing to load the model’s weights onto the target accelerator.

Model architecture + hardware specs + batch and parallelism
→ operation costs → decode-step time → TPS/user → capacity curve

1. Describe the work. AISim’s model definitions represent the four architectures as graphs of operations: attention projections, cache access and attention, routed expert computation, and communication between chips. Layer counts, matrix dimensions, expert counts and experts selected per token determine how much work is required. Each candidate specifies its batch and supported TP/DP/EP/ETP/DCP/PP layout, with 262,144 cached tokens per request. MAI-2 uses the native STEP3P7 graph; its search does not support DCP.

2. Price each operation against hardware resources. Hardware profiles supply compute rates at the relevant precision, HBM bandwidth and capacity, and interconnect bandwidth and scale-up sizes. For a roofline-modeled compute operation, the core calculation is:

Compute time = required arithmetic operations ÷ peak operations/second
Memory time = modeled HBM bytes moved ÷ HBM bytes/second
Operation time ≈ max(compute time, memory time)

A simple example. Moving 80 decimal GB through 8 TB/s of HBM bandwidth takes 10 ms at peak rate. If that operation’s arithmetic takes 4 ms at peak compute, its roofline time is 10 ms, not 14 ms: memory is the limiting resource. Required non-overlapped communication and subsequent operations still add time. These are illustrative numbers, not a measured model run.

This asks which resource limits that operation. More bandwidth helps a weight- or cache-reading bottleneck; more FLOPs help a compute bottleneck. The byte counts depend on the architecture, precision and sharding. For MoE, the model distributes routed work across expert ranks and caps expert-weight reads at the resident expert inventory. Attention uses the model’s own attention pattern rather than treating every architecture as full attention.

3. Include communication and combine timings. AISim charges the collectives required by the chosen layout, using their transfer volumes, participant counts and the hardware profile’s link rates. Our hardware policies determine which scale-up and scale-out paths a layout can use; TPU v8i also receives the study’s explicit hop-latency adjustment. The study sums the emitted operation timings across the model. Where AISim explicitly represents overlapping branches, it takes the longer branch duration instead of adding both. Consequently, the result is an operation-by-operation estimate, not simply total model FLOPs divided by chip FLOPs.

4. Convert a speculative step into output speed. The current score uses nextn=3: four target verification positions, with an assumed average accepted length of 3 output tokens per iteration. AISim’s native model graph includes verification and its model-specific draft-work representation. We divide that complete modeled iteration time by the accepted length:

TPOT = iteration time ÷ 3
TPS/user = 3 ÷ iteration time in seconds
Example: 23.097 ms per iteration → 7.699 ms/output token → 129.885 TPS/user

5 · Why these precisions?

Hardware-adapted modeling policy

Low-bit expert weights reflect the intended co-optimized inference scenario. FP8 is retained where our hardware profiles do not support FP4. FP4-capable profiles use the native NVFP4 analytical representation even when the hardware advertises another format; this is not bit-exact format equivalence.

BF16 non-expert GEMMs and FP8 KV are fixed study settings, with the native Kimi FP8 decode-MLA exception. We do not establish equal model accuracy, format-specific overhead or equivalent kernel efficiency across vendors.

AL3 is a shared assumption, not measured acceptance for every architecture. Native full-GQA and SWA verification can pessimistically repeat prefix reads. Precision is hardware-adapted FP4 experts via an NVFP4 analytical proxy, except H100, H200 and TPU v7 using FP8 experts. Non-expert GEMMs use BF16; the nominal attention setting is BF16, but the native Kimi decode-MLA path uses FP8. KV storage is FP8. These modeling choices do not establish equal accuracy across formats or models.[5]

5. Search for capacity at each speed. Our wrapper evaluates supported layouts and every admitted integer batch in the search. Admission accounts for model weights, KV cache, workspace and fixed reservations, using the study’s 90% configured fraction, backend-specific pool semantics and additional guards. Each candidate produces a speed and a density: concurrent requests divided by allocated chips. At every speed threshold, we select the highest density among candidates that meet it. Those selections form the decode step frontier; adding the prefill resource term gives the combined curve scored above. This is an optimum over saved candidates, not proof of the global best serving implementation.

How to interpret SOL. The score uses peak-resource estimates with performance corrections disabled. It describes the performance implied by the modeled operation graph and hardware specifications; implementation efficiency, memory reuse and communication assumptions determine how closely a deployed system can approach it. The headline applies no utilization discount.

Implementation reference. The current runs use AISim commit 2f0f4cd8606d580567b253d02f3d699fe36db865. The engine is unchanged; the MAI-2 study adds a process-local architecture adapter composed of native operators, not an upstream-supported MAI implementation. studies/mai2_swa.py and studies/mai2_prefill.py supply its phase sweeps and heterogeneous-layer memory guards. src/agent_index/index.py constructs decode envelopes; studies/log400_release.py integrates combined capacity over log speed and assembles the four-model index. Finite searches, conservative serial pipeline scheduling, topology assumptions and ideal expert balancing limit the result; this is not an SGLang scheduling trace.

What SOL establishes—and what needs benchmarking

AISim makes a consistent operation-level comparison possible without access to every accelerator or equally optimized serving implementations. It estimates the constraints implied by the model graph and hardware specifications. That is useful for cross-hardware roofline analysis, while actual benchmarks are needed to establish achievable efficiency.

Reading an efficiency percentage. If SOL predicts 200 TPS/user for a given configuration and concurrency, achieving 50% of that speed means 100 TPS/user and twice the modeled time per output token. It does not mean half the latency, or automatically half the maximum concurrency at a speed target. Real deployments can lose performance to kernel efficiency, scheduling, load imbalance and communication overhead; the achieved fraction can differ by hardware and workload.

A ceiling conditional on the model. This is not a proven upper bound over every possible implementation. Fusion, better data reuse or a different communication algorithm can change the modeled work itself. Beating an imperfect SOL estimate would expose a modeling assumption, not exceed the chip’s physical limits. Likewise, overly optimistic traffic or topology assumptions can overstate the achievable speed.

It is not a cycle-accurate reproduction of each chip. Memory reuse, expert balance, communication, speculative verification and vendor-specific execution remain modeling assumptions. Benchmark grounding on some configurations does not guarantee the same achieved fraction on every platform. The score measures modeled hardware capacity for this workload—not model quality, API pricing or measured concurrent-user capacity.

STEP 3 · SEARCH SERVING CONFIGURATIONS

Find the most decode concurrency that meets each speed target

6 · Why this search and memory budget?

Finite search and admission assumptions

We search supported layouts and admitted integer batches rather than prescribing one rack-wide configuration. Only allocated chips count. Integral expert placement and platform scale-up limits constrain the candidates; node-restricted systems use serial pipeline stages across nodes.

The configured memory fraction is 90%, with native workspace, a 4GiB fixed reservation and additional guards. For Kimi’s SGLang path, this fraction governs the static pool after pre-load overhead; displayed totals also include transient activations and can exceed 90%. The other plotted models use a total-memory budget. These are study conventions, not vendor-calibrated usable-memory limits.

For each hardware/model pair, we evaluate supported parallelism layouts and integer batches. We reject configurations that fail the memory-admission rules. At a target such as 100 TPS/user, retain the candidates fast enough to meet it and choose the highest concurrent-request count per allocated chip.[6]

Cdecode(s) = max [concurrent requests ÷ allocated decode chips]
over saved memory-feasible candidates with modeled TPS/user ≥ s

Repeat that selection at every speed threshold. A higher requirement usually forces a smaller batch or a different layout. The deployment chip limit is a ceiling, not a requirement to occupy a whole rack: only allocated chips count.

Memory admission, parallelism and the limits of this search

Admission accounts for weights, KV cache, workspace, fixed reservations and guards using a 90% configured memory fraction, with Kimi’s static-pool exception described in step 5. Layouts use supported TP/DP/EP/ETP/DCP/PP combinations with integral expert placement. For node-restricted systems, cross-node deployment uses the study’s conservative serial pipeline schedule; MAI-2’s decode search uses DCP1.

This is the best result among saved candidates—not proof of the best possible implementation. Integer batches and configuration switches produce steps. A candidate exactly at the speed threshold remains eligible; if none qualify, capacity is zero. The explorer in step 5 shows the winning layouts and a worked explanation of their labels.

STEP 4 · PROVIDE THE INPUT WORK TOO

Add the prefill chips required by the same workload

7 · Why 1Ki new input and throughput?

Representative warm-input proxy

1,024 new tokens over the existing context represents a short warm-cache input phase and reuses our aligned prefill sweeps. The selected trace cohort averages about 1,423 new tokens; 1,024 is a convenient study point, not that exact mean.

We optimize throughput because this term budgets the accelerator resources needed to supply input work. It does not impose a time-to-first-token SLA. Using the 1Ki per-token rate for the whole cohort approximates its input-length distribution; larger inputs can have different efficiency.

Independently optimize prefill for maximum new-input tokens per allocated chip-second: 262,144 cached tokens plus 1,024 new tokens per request, without a latency target or speculative decoding. Call that rate P.[7]

8 · Why 1.513 input/output?

Saved trace measurement

The warm-cache cohort has 110,565 requests, mean new input 1,422.854 and mean output 940.206 tokens. Dividing aggregate new input by aggregate output gives 1.5133425. The saved query selects Claude-provider requests with positive output, ≥90% cached input, 128–384Ki cached tokens and 1–10Ki new tokens.

This conditions the ratio on the study’s warm long-context workload. It excludes cold misses and is not a universal agent traffic ratio. We apply it to every model without adjusting tokenization or verbosity. Exact query and artifact hashes are in the companion data and the trace-grounding expander.

The selected coding-trace cohort supplies the workload ratio: 1.513 new input tokens per output token. Faster output therefore requires proportionally more input-processing throughput. Each hardware/model pair supplies its own prefill rate; there is no fixed 15% weighting.[8]

9 · Why add chip budgets?

Steady-state resource accounting

One continuously decoding request at target speed s needs r × s new input tokens processed per second on average. Dividing that demand by the best prefill rate gives prefill chips per request; adding decode chips per request yields total resource demand.

This automatically changes the phase allocation with each chip’s strengths. It assumes same-chip-type, fully utilized pools, fleet-scale fractional allocation and resident caches. Transfers, scheduling and extra cache-placement overhead are not included.

A stronger prefill chip needs a smaller input-processing pool; a stronger decode chip can change that balance in the other direction. We therefore add the resources needed for the same workload, rather than applying the same percentage blend to every chip.[9]

At target output speed s, let C(s) be decode agents per decode chip, P be new input tokens per prefill chip-second, and r = 1.5133425 be new input tokens per output token:

Decode chips per agent = 1 / C(s)
Prefill chips per agent = r × s / P
Combined agents per total chip = 1 / [1/C(s) + r × s/P]
Prefill chip share = (r × s/P) / [1/C(s) + r × s/P]

The phase share varies with hardware, architecture and target speed. Combine the capacities before calculating log-speed area and normalizing to GB300.

This is ideal fleet-scale allocation between separately provisioned, fully utilized pools of the same chip type. Output is paced at the requested target, rather than assuming all of a selected configuration’s extra speed is used. “Agents” means concurrent decoding requests after provisioning their input work—not wall-clock concurrent users including tools, idle time or waiting. We do not simulate mixed-batch contention or prefill/decode transfers here.

Trace grounding: cohort, token ratio and representativeness

It is informed by the public Syfi coding trace v0.0.2 numeric request data analyzed in TraceLab. The saved warm-cache cohort contains 110,565 requests, averaging 1,422.854 new input tokens and 940.206 output tokens. Their ratio is 1.513342523752522.

r = sum of new input tokens / sum of output tokens
= mean new input / mean output for the same request cohort

The cohort selects Claude-provider requests with positive output, at least 90% of total input already cached, 131,072–393,216 cached tokens, and 1–10,240 new input tokens. Cached tokens are not included in the numerator.

We reuse the saved cohort statistics, query and database hash—not a fresh database extraction in this explainer update. This is a warm-cache coding-workload estimate, not a universal traffic distribution. The simulator still uses a fixed 262,144-token prefix and a 1,024-new-token prefill rate; it does not replay the cohort’s input-length distribution. Prefill optimization: winning configurations and a numerical example

Workload. Every request has the architecture-specific cache for its own 262,144-token prefix resident on the worker. It then receives 1,024 new input tokens. The forward pass processes those new tokens using the existing cache, subject to the model’s attention pattern. We count only the new tokens as throughput—not the cached prefix. Prefill has no speculative decoding (nextn=0), unlike the decode curves.

Optimization. Independently of the decode winners, choose the memory-admitted layout and batch with the highest new-input tokens per allocated chip-second. Prefill throughput P has no latency floor or separate AUC; it supplies the input-work term in the combined curve. If B is requests per attention-DP group, D is the group count, N is allocated chips and T is the modeled forward duration in seconds:

Prefill throughput P = (B × D × 1,024) ÷ (N × T)

Deployment assumptions: separate pools and cache placement

The current scores use the same accelerator type in both pools, with each pool independently optimized. Fractional prefill-chip counts represent a large fleet sharing that capacity across many decode instances, not fractions of individual machines.

Each phase is modeled with its required cache already resident. A real deployment must arrange that placement: a prefill worker needs access to the existing prefix before processing new input, and the decode worker needs the resulting KV afterward. The phase simulations include their own resident-cache memory costs, but the combination does not track cache lifetimes or charge additional fleet-level duplication and transfer costs. It is an ideal resource budget, not a complete disaggregated-serving simulation.

STEP 5 · COMPARE A RANGE OF INTERACTIVITIES

Measure the area under each combined-capacity curve

10 · Why log 50–400 AUC?

Equal weight per speed doubling

A proportional speed improvement has the same horizontal span anywhere in the band: 50–100, 100–200 and 200–400 each receive one third of the integration weight. This balances slower throughput-oriented work with faster interactive work. A range avoids hinging the index on one target near a configuration switch. Equal log-speed weight is a benchmark convention, not a measured demand distribution; actual area also depends on supported capacity.

For illustration only, 50% of SOL speed at fixed concurrency would turn this into 25–200 achieved TPS/user. Neither that efficiency nor the endpoint choices are universal. If a deployment has a known speed SLA, its pointwise capacity is more directly relevant.

Plot minimum output speed on the horizontal axis and decode concurrency per total prefill + decode chip on the vertical axis. Integrate over 50–400 SOL TPS/user on a logarithmic speed axis. More area means more supported capacity across this range of speed requirements.[10]

Equal weight per doubling: 50–100, 100–200 and 200–400 each occupy the same width. This gives slower throughput-oriented agents and faster interactive agents a balanced place in the comparison. Equal width means equal integration weight—not equal area, which also depends on capacity.

For each model, divide the hardware’s area by GB300’s area. The tabs below show this calculation; move the slider to inspect the selected decode configuration and its added prefill allocation.

Choosing an AUC instead of a single speed target

A single target is appropriate for a deployment with one known speed requirement. The index instead summarizes a range of acceptable interactivities, avoiding dependence on one threshold that may sit just before or after a configuration switch. The explorer still shows individual targets, so the summary need not replace a workload-specific comparison.

Log weighting treats proportional speed changes consistently: doubling from 50 to 100 has the same integration weight as doubling from 200 to 400. The band and weighting are declared benchmark choices, not a statistically estimated user preference. A known application’s speed requirements can instead be evaluated directly in the explorer.

We divide the two capacity areas, rather than averaging pointwise hardware/GB300 ratios. Where GB300 capacity is positive, this amounts to weighting the relative advantage by GB300’s capacity as well as the speed-axis weight. Large percentage advantages where baseline capacity is tiny therefore do not automatically dominate. A hardware’s feasible region still contributes area where GB300 has no feasible candidate.

Why 50–400, and how is log area calculated?

The band includes slower throughput-oriented workloads and faster interactive ones without making ultra-fast specialist serving the headline. Each doubling receives one third of the speed-axis weight. This is a transparent way to cover several operating regimes without assuming a specific distribution of demand.

Area = ∫50400 Ccombined(s) d ln(s) = ∫50400 Ccombined(s) ds / s

Between saved decode-speed breakpoints, decode capacity c is constant and combined capacity is c/(1 + rsc/P). Its exact log-speed area from a to b is c × ln[b(1 + rca/P) / (a(1 + rcb/P))]. We sum every segment; unsupported speeds contribute zero. The display grid does not determine the score. Dividing by ln(400/50) would express an average capacity, but cancels in the hardware/GB300 ratio. The log base also cancels.

At an illustrative 50% of modeled SOL speed at fixed concurrency, 50–400 SOL TPS/user corresponds to 25–200 achieved TPS/user. That is a scenario, not a universal calibration: implementation, configuration and hardware can change the achieved fraction. We apply no such discount to the index itself.

What do the parallelism labels mean? A worked example

On GB300, the selected layout is TP4 DP16 DCP4 ETP2 EP32 PP1. These are different ways of organizing the same 64 chips, not six factors to multiply together.

LabelMeaning in this example
TP4 — tensor parallelismFour chips cooperate on sharded attention projections and other non-expert tensor work for each request group. TP is still relevant when DCP equals TP.
DP16 — attention data parallelism16 groups handle different requests. Each group has 4 chips and a batch of 57 requests. These are not 16 independent full-model copies: they share the distributed expert layer.
DCP4 — decode context parallelismThe cached sequence and context-attention work are partitioned across the 4 chips within each TP group, with partial results merged. It uses the existing chips; it does not multiply the chip count again.
EP32 — expert parallelismThe routed experts are distributed into 32 partitions across that same chip set. This is a partition count, not the number of experts selected by each token.
ETP2 — expert tensor parallelismEach expert partition’s matrices are sharded over 2 chips. Thus the expert view is 32 × 2 = 64 chips, matching the attention view of 16 × 4 = 64.
PP1 — pipeline parallelismOne stage, so layers are not split across additional pipeline stages. In general allocated chips = TP × DP × PP = ETP × EP × PP.

57 requests/group × 16 groups = 912 concurrent requests
912 ÷ 64 allocated chips = 14.25 requests/chip
23.097 ms/speculative step ÷ AL3 = 7.699 ms/output token → 129.885 TPS/user, exceeding the 100 target.

The admission ceiling is 90% = 241.40 GiB; this usage already includes the study’s reservations and guards. A 72-chip deployment ceiling does not force use of 72: only the 64 allocated chips enter this density. At a different speed target, another layout or batch can win.

At a paced 100 TPS/user, the input supply requires 1.5133425 × 100 × 912 ≈ 138,017 new tokens/s. With GB300 prefill throughput of 24,325.9 new tokens/chip/s, allocate the equivalent of 5.674 prefill chips in addition to the 64 decode chips. Combined density is 912 ÷ 69.674 ≈ 13.090 agents/total chip. This is a fleet-average resource budget, not a claim that a six-chip prefill layout was simulated.

STEP 6 · SUMMARIZE THE ARCHITECTURE BASKET

Normalize each model first, then average the four scores

11 · Why GB300 and equal model weights?

Normalization and basket convention

GB300 is the study’s reference platform. Dividing each model’s area by its own GB300 area removes raw request-capacity units before combining models; a small model cannot dominate merely because it fits more requests. Each architecture then receives one quarter of the arithmetic average.

Equal weights are an explicit architectural-coverage choice, not estimated traffic shares. The score remains sensitive to the basket and is neither quality-adjusted nor a cost/power-normalized hardware exchange rate. Frozen versions and visible component scores make that dependence auditable.

Each model contributes one GB300-relative combined-area ratio. Their equal-weight arithmetic mean is the headline index. This prevents models with higher raw request capacity from dominating simply because they support more requests.[11]

Interpreting model-mixture sensitivity

The variation is real within the model: different attention/cache patterns, expert work, memory fit and communication expose different hardware advantages. An average is useful as a defined basket score, not as a universal multiplier. We normalize each model to GB300 first, then give the four architectures equal weight so raw capacity on one model cannot overwhelm the others.

For example, the current combined calculation gives VR200 1.24× on GLM and 2.74× on Kimi. Qwen and MAI-2 broaden architectural coverage; they do not remove model-mixture sensitivity. Use the per-model table and curves whenever the intended architecture is known. Equal model weights express a benchmark choice, not known traffic shares or a statistical confidence interval.

Versioning the index and testing stability over time

Stability across successive model generations has not yet been established. Additional architecture studies and older saved runs are not a same-engine, same-policy backtest across actual frontier checkpoints. Hypothetical larger models cannot substitute for that test. Stable ordering in a limited sensitivity study also does not establish stable GB300-equivalent magnitudes.

Treat a score as belonging to a fixed version of the model basket, workload, hardware profiles and simulator. A future model update can legitimately change it. For longitudinal comparisons, retain the frozen version; when publishing a new basket, rerun the compared hardware consistently and show old/new results side by side. The current index should not be treated as an immutable physical conversion factor.

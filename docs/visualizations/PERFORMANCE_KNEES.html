Reading the knees in inference performance

Adding more concurrent requests spreads weight reads over more output tokens—but also adds compute, cache traffic and communication. Several different effects can make a curve bend. They should not all be called “saturation.”

Inference Capacity Index v1 · saved AISim SOL results plus explicitly labeled teaching examples · no new accelerator predictions

Historical teaching curves (15 October): Rubin here retains the original 22 TB/s HBM and 1.8 TB/s outbound NVLink profile. These fixed-layout examples are not the revised October 20 index frontiers shown in the main explainer.

A knee point is a bend or change in slope. It can reflect a resource limit, but it can also arise from changing axes or selecting a different configuration. This page separates those explanations.

1 · Saved curves2 · Changing axes3 · Expert coverage4 · Resource crossover5 · Diagnose a knee

Expert-weight coverage

Once a batch touches the resident expert inventory, more tokens no longer require new distinct expert weights for that operation. Expert computation still grows.

Bandwidth ↔ compute

An operation changes bottleneck when its compute time exceeds its memory-transfer time, or vice versa. Different operations can be limited by different resources in the same step.

Memory-capacity ceiling

Weights, KV and reservations fill the admitted HBM budget. This stops the batch from growing; it does not itself make each step compute-bound or bandwidth-bound.

A useful rule for doubling concurrency

Doubling concurrency changes throughput by 2T(n)/T(2n), and TPS/user by T(n)/T(2n), for fixed layout and accepted length. If TPOT rises 10%, throughput rises about 82%, while TPS/user falls about 9%. If TPOT doubles, throughput is unchanged and TPS/user halves. Use the actual T values; “all experts covered” alone cannot tell you which case applies.

2. One straight latency line, four different-looking plots

Interactivity = output TPS/user. Token throughput is output tokens per chip-second; concurrency is requests per chip. Confusing those vertical axes can make the same data appear to tell different stories.

For a fixed layout, suppose TPOT is approximately T(n) = a + bn, with n concurrent requests per chip and time in seconds. The intercept a represents approximately batch-shared time in the regime being examined; b represents the extra time per added request. For example, covered expert-weight reads can contribute a shared cost, while compute and cache traffic grow with n. These coefficients are a local approximation—not a universal physical decomposition.

Interactivity s = 1/T(n) = 1/(a + bn)
Token throughput/chip Q = n/T(n) = n/(a + bn)
Eliminating n: Q(s) = (1 − as)/b
Concurrency/chip n(s) = Q(s)/s = (1/s − a)/b

The surprising part: a straight TPOT–concurrency line produces a flattening throughput–concurrency curve, but a straight throughput–interactivity line. Concurrency–interactivity is curved because we divide by speed once more.

Illustrative only: T(n) = 10 + n milliseconds. No memory ceiling is applied here; the displayed n=1–80 range is chosen for teaching. Orange dots identify the same operating point on all four panels.

Why does throughput flatten while TPOT keeps rising?

At low concurrency, more requests spread the fixed 10 ms over more output tokens. At large concurrency, the n milliseconds of per-request work dominate: doubling n nearly doubles elapsed time. Token throughput approaches 1,000 tokens/chip/s, while TPS/user continues toward zero. This plateau can result from compute, cache bandwidth or another cost proportional to concurrency; its existence alone does not identify the resource.

For general positive a and b, Q(n) approaches 1/b, with slope a/(a+bn)². At n=a/b, the shared and growing time terms are equal, and throughput is half its asymptote. That is a smooth amortization knee—not necessarily a new hardware bottleneck. If a were zero, the linear-latency model would give constant throughput from the outset.

Why is throughput versus interactivity straight, but concurrency versus interactivity curved?

In this example, Q(s) = 1,000 − 10s. Every extra 10 TPS/user costs 100 output tokens/chip/s along this fixed-layout relationship. But concurrency is Q/s = 1,000/s − 10, an inverse curve. These formulas describe the modeled operating range, not a valid extrapolation to negative throughput or zero requests.

Even with completely constant throughput of 1,000 tokens/s, the same system supports 20 decoding requests at 50 TPS/user, 10 at 100 TPS/user, or 5 at 200 TPS/user. The inverse shape appears without any resource transition at all. Conversely, the token-throughput/interactivity line bends when the latency law changes, such as expert-coverage saturation, a roofline crossover or layout selection.

How does this relate to the index’s capacity-versus-interactivity frontier?

The native plots above use modeled SOL speed for each batch, not measured achieved performance. The index instead asks for the largest concurrency meeting a minimum speed threshold. For a continuous fixed-layout approximation with memory ceiling nmax, decode capacity would be min[nmax, (1/s − a)/b], within the range where at least one request fits and meets the target.

In this fixed-layout example, sufficiently low thresholds admit the largest memory-feasible batch: relaxing the target further cannot add requests, so decode capacity is flat. At higher thresholds, the speed requirement forces lower concurrency. The index combines integer batches and multiple layouts, giving steps and configuration switches rather than a smooth inverse curve. A configuration with modeled speed above the threshold can remain the winner across an entire interval; a flat region alone does not prove that physical HBM is full.

The current combined index then counts prefill chips too: Ccombined(s) = Cdecode(s) / [1 + r × s × Cdecode(s)/P]. Even when decode capacity is flat, increasing the target provisions more prefill chips, making combined concurrency per total chip slope downward. This is resource accounting—not evidence that the decode kernels changed bottleneck. Multiplying combined capacity by s gives the corresponding paced output throughput per total chip; the index plots capacity, not that token-throughput quantity.

Read the axes before diagnosing a knee. Curvature can come from a reciprocal, a capacity cutoff, or changing the selected configuration. A bottleneck claim needs evidence from the operation costs.

3. When are all experts activated?

In the current simulator, this means a cap on expert-weight reads—not a prediction of routing coverage. Let E be experts per routed layer, k experts selected per token, and N the token positions entering that layer across the expert-parallel group.

Approximate native weight-read count = min(E, N × k)
Integer rank form = min(E/EP, floor(N × k/EP)) per expert rank
Main verification: N = B × DP × 4; ordinary decode: N = B × DP

The cap is reached at N ≥ E/k for valid evenly divisible layouts. It does not change the per-token top-k: each token still selects k experts, not E. All weights are already allocated in memory before this point; coverage changes which weights are read during an operation, not which weights must fit.

Why actual routing need not touch every expert at that point

If each position independently selects k distinct experts uniformly, the expected number touched is E × [1 − (1 − k/E)N]. At roughly E/k positions, that is only around 63% of the expert inventory, not all of it. Approximately three times as many independent positions are needed for 95% expected coverage. “95% expected coverage” is not a 95% probability that every expert is touched.

Real routing can be nonuniform and correlated, especially between adjacent speculative positions. That can reduce distinct coverage or concentrate work on a few ranks; the most loaded rank can determine step time. The green curve is a mathematical comparison, not measured routing and not used in the score. There is no universal request count at which all real experts become active.

The native rank formula also floors token assignments. At very small batches it can undercount rank traffic, including assigning zero modeled expert-weight reads when N × k is below EP. This is a modeling artifact, not physically free execution. The purple marker concerns the main verification MoE; separately represented draft operations need not reach their cap at the same request count. AL3 affects accepted output/time, not the four-position verification input size.

4. Expert coverage is not the compute crossover

For each roofline-modeled operation, use max(compute time, HBM time). After expert-weight coverage saturates, the fixed weight-read term stops growing, but compute and activation traffic continue to grow with token count. That can produce a later bandwidth-to-compute crossover.

The exact illustrative equations

HBM time = [2 × min(B/8, 1) + 0.005B] / bandwidth multiplier
Compute time = 0.015B
Total time = max(HBM time, compute time) + 0.3 + 0.02B
Admission ceiling: B = 96; all times in illustrative milliseconds

Expert reads cap at B=8. The +0.005B term represents activation traffic; +0.3+0.02B represents sequential work outside this MoE operation. At bandwidth multiplier 1, the post-coverage crossover is B=200, beyond the capacity ceiling. Faster HBM moves that crossover to a smaller B; capacity itself stays at 96. This illustrates why a compute-bound regime may exist mathematically but never be reached before memory fills.

5. How to diagnose a knee in practice

What changed?What it can meanWhat to check
Weight-read slope flattensMore requests reuse an already covered expert inventory.Distinct-weight byte counts versus token assignments. Compute and cache costs may still rise.
An operation changes slopeCompute overtakes HBM time, or an integer partition changes.Separate FLOP and byte times for that operation—not just end-to-end latency.
A fixed-layout curve endsThe next batch fails memory admission.Weights + KV + workspace + reservations + guards versus usable HBM. This is not a throughput plateau.
The optimized capacity frontier jumpsA different layout or integer batch wins at the new speed target.The selected TP/DP/EP/ETP/DCP/PP and batch on both sides. A frontier kink need not be a resource crossover.
More bandwidth stops helping muchRemaining compute, communication or other sequential work limits the gain.Per-operation times and collective costs. Faster HBM does not automatically improve either.

Cache storage and cache reads per step are separate. Full attention revisits a long prefix; sparse attention can read a subset while still retaining much of the cache, with index work adding its own cost. Sliding-window layers can reduce both retained cache and reads, but a minority of global layers can still matter. More capacity extends feasible concurrency; more bandwidth changes time for bandwidth-limited work.

The saved fixed-layout CSVs above contain total timing and memory admission, not enough operation-level breakdown to certify a specific compute/communication crossover. The expert-cap markers are derived from the inspected native formula. We do not infer a measured bottleneck solely from the shape of a total-time curve.
